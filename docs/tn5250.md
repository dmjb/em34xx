# TN5250 client (`src/tn5250`)

The host side of the Twinax bridge: a TN5250 client that keeps the 5250
presentation space of one display station in a *shadow screen*, with the
station's format table, keyboard state and operator field editing. The
virtual workstation controller (`src/host/wsc`) paints the emulated
terminal from the shadow and feeds operator functions back in, through
`tn5250::DisplaySession` (`session_api.hpp`). Nothing in `src/tn5250` knows
about Twinax.

Clean room: written from the RFCs and the IBM *5494 Remote Control Unit
Functions Reference*, SC30-3533-04 ("FR" below). Other clients and
emulators were used only to check behaviour; no code or data comes from
them.

## Layers

| File | Role |
| --- | --- |
| `session_api.hpp` | the interface the controller uses: cells, cursor, indicators, operator functions, AID keys, record sink |
| `transport.*` | byte transport: plain TCP, or TLS through `tls_*.cpp` (see below) |
| `telnet.*` | telnet option negotiation and record splitting; pure state machine |
| `record.*` | RFC 1205 logical record header |
| `engine.*` | the 5250 data stream engine: shadow, format table, reads, editing |
| `client.*` | `Client`: a session driven by `Tn5250Config`, with its own I/O thread |
| `codepage.*` | EBCDIC tables for CCSID 37, 500 and 273 |
| `src/tools/tn5250_probe.cpp` | `tn5250-probe`, a live test tool |

### Threads

`Client` runs the transport and telnet layer on its own thread. Complete
records go into a mutex-protected queue. The owner calls `pump()` on its
own thread (the emulation thread) to apply them to the engine. Replies from
the engine are framed and queued, and the I/O thread sends them. The engine
itself is single-threaded.

## Telnet negotiation

The server leads; the client answers. It replies only when an option's
state changes, so negotiation cannot loop (RFC 854).

| Option | RFC | Client behaviour |
| --- | --- | --- |
| BINARY | 856 | WILL and DO |
| END-OF-RECORD | 885 | WILL and DO |
| TERMINAL-TYPE | 1091 | WILL; `SEND` is answered `IS <type>` |
| NEW-ENVIRON | 1572, 4777 | WILL; `SEND` is answered `IS` with the requested variables |
| TIMING-MARK | 860 | `DO` is answered `WILL`, without enabling anything |
| others | | refused with WONT or DONT |

The session reaches 5250 transparent mode once BINARY and EOR are agreed in
both directions and the terminal type has been sent.

**Terminal type.** It is derived from the emulated model and the display
subtype. A colour 3477 presents `IBM-3477-FC`; green, amber and paper-white
present `IBM-3477-FG`. A per-station `profile`, or `--tn5250-type` /
`tn5250.terminal_type`, overrides the derived type. The engine builds its
Query Reply from the type, so the screen-size and colour claims follow the
model.

**Environment (RFC 4777 section 4).** The client sends only what is
configured:

- `USERVAR DEVNAME`, if a device name is set.
- `KBDTYPE`, `CODEPAGE` and `CHARSET`, together. For CCSID 37 these are
  derived as `USB`/`37`/`697`. For other code pages they are sent only if
  `KBDTYPE` is given in `tn5250.env`.
- Any further `tn5250.env` entries. The RFC 1572 standard names go as
  `VAR`; everything else goes as `USERVAR`.

The client never sends `USER` or a password on its own initiative. Values
are ESC-quoted, and IAC bytes are doubled.

**Password substitution (RFC 4777 section 5).** If the server asks for
`IBMRSEED<seed>`, the client records the seed and logs it, but sends no
`IBMSUBSPW`. Auto sign-on would need DES or SHA-1 password substitutes and
stored credentials. Neither is implemented.

## Records (RFC 1205 section 3)

Each record has:

- a 10-byte header:
  - logical length,
  - record type `12A0`,
  - reserved,
  - variable header length `04`,
  - flags (`80` ERR, `40` ATN, `04` SRQ, `02` TRQ, `01` HLP),
  - a reserved byte,
  - the opcode;
- the 5250 data stream;
- `IAC EOR`.

| Client record | Opcode | Flags |
| --- | --- | --- |
| AID replies to Read Input / Read MDT | 03 Put/Get | |
| Save Screen reply (`04 12 …`) | 04 | |
| Query Reply, Read Immediate, Read Screen | 00 | |
| Cancel Invite acknowledgement | 0A | |
| Attention | 00 | ATN |
| System Request | 00 | SRQ |
| Help in error state (packed error code) | 00 | HLP |
| Negative response (4-byte sense) | 00 | ERR |

Opcodes `0B` and `0C` from the host turn the message-waiting light on and
off.

The logical length is 16 bits, so a record carries at most 65 525 data
bytes; `encode_record()` refuses more. Inbound, the telnet layer fails the
session ("record exceeds ... without IAC EOR") when a record passes
65 535 + 1024 bytes, and likewise for a subnegotiation over 4096 bytes with
no `IAC SE`.

`Client` bounds what it holds between its two threads. While 4 MiB of host
records wait for `pump()` it stops reading the socket; more than 4 MiB of
unsent replies fail the session; its log keeps the newest 500 lines. An
exception on the I/O thread fails the session.

## Data stream coverage

### Commands (FR 15)

| Code | Command | Notes |
| --- | --- | --- |
| 40 | Clear Unit | 24×80, nulls, no fields, keyboard locked |
| 20 pp | Clear Unit Alternate | `00` = 27×132 when the type supports it, otherwise sense `10030101`; `80` = keep the size; any other value gives `10030105` |
| 50 | Clear Format Table | |
| 11 | Write To Display | CC0 is applied first (FR Table 43) and CC1 last (Table 44). CC1 is skipped after a parameter error |
| 21 | Write Error Code | No control bytes. Optional IC; text goes on the error line |
| 22 | Write Error Code to Window | Columns sc..ec of the error line |
| 42, 52, 82 | Read Input Fields, Read MDT Fields, Read MDT Alternate | Arm a read. A held AID is answered at once |
| 72, 83 | Read Immediate, Read Modified Immediate Alternate | Answered immediately with AID `00` |
| 62 | Read Screen | The buffer, raw, one byte per cell |
| 02, 03 | Save Screen, Save Partial Screen | The reply starts `04 12` (or `04 13 LL`); our image follows |
| 12, 13 | Restore Screen, Restore Partial Screen | Only our own image is accepted; anything else gives `10050127` |
| 23 | Roll | Vacated lines keep their contents (FR 15.25) |
| F3 | Write Structured Field | 5250 Query (`D9 70`) gets a Query Reply. Other structured fields are skipped |
| F4 | Write Single Structured Field | Skipped |

Anything else gets sense `10030101`.

### Limits per host record **[design]**

No real session comes near these. They keep a hostile or broken host from
turning a small record into megabytes of replies or seconds of work.

| Limit | Value | Over the limit |
| --- | --- | --- |
| Replies to one record (Read Immediate, Read Screen, Save Screen, a Query, a read answered by a held AID) | 4 | sense `10030101`; the rest of the record is not processed |
| Cells touched by repeat-type operations (RA, EA, Clear Unit, a non-zero CC0, Roll, Restore Screen, Write Error Code) | 64 × 27×132 | sense `10030101`, likewise |
| FCWs in one SF | 32 | sense `10050129` |

A host sends one read-type command per record, and a screen build repeats
over a few screens' worth of cells at most. With 256 fields of 32 FCWs the
save image stays under 32 KiB, so its 16-bit lengths cannot wrap.

### Orders inside WTD (FR 15.6)

SBA, IC, MC, RA, EA, SOH, TD, WEA, SF (with FFW and FCWs), and WDSF, which
is skipped because no GUI support is claimed.

- Each order is walked by its own length, so an `04` byte inside an order's
  operands does not end the command.
- SOH is skipped by its length byte.
- A byte below `0x40` that is not an order takes one position.
- An input SF writes an ending attribute `20` after the field, unless that
  position already is the leading attribute of the next field **[design]**.
- A field occupies its leading attribute, its data and its ending attribute.
  Two fields may share one attribute position (the ending attribute of one
  is the leading attribute of the next). An SF whose extent overlaps other
  fields any further removes them from the format table, whether it defines
  a new field or changes the length of an existing one.

### Fields, MDT and reads

- **FFW** (FR Table 47) supports these:
  - bypass;
  - Dup / Field Mark enable;
  - MDT;
  - the shift/edit types: alpha shift, alpha only, numeric shift, numeric
    only, digits only, I/O and signed numeric;
  - auto enter;
  - Field Exit required;
  - monocase;
  - mandatory enter;
  - right adjust with zero fill (`101`) or blank fill (`110`), as Table 47
    gives them. Table 48 gives the two values the other way round;
  - mandatory fill.
- **FCWs** used: resequencing `80nn`, transparency `84nn`, forward edge
  trigger `8501` and cursor progression `88nn`. Other FCWs are stored but
  have no effect.
- **Read MDT** sends `11 row col data` for each MDT field. Trailing nulls
  are stripped, and leading and embedded nulls become blanks.
- **Read MDT Alternate** keeps those nulls.
- **Read Input Fields** sends every field padded to its length, with no
  SBA. It sends data only when some MDT is on.
- **Signed numeric** fields drop the sign position. A `-` sign sets the D
  zone on the low-order digit.
- **Transparent** fields are sent as `11 row col 10 LLLL data`.
- **AIDs that carry data:** Enter, the Roll keys, and PF1–24 (unless masked
  by SOH bytes 5–7). Clear, Help, Print, Record Backspace and PA1–3 send
  only the cursor and AID.

### Query Reply (FR 15.27.2, RFC 1205 section 5)

The reply is `00 00 88` followed by a 68-byte `D9 70 80` structured field:

- controller class `0600` ("other 5250 emulator");
- machine type `3477` and model `0FC` or `0FG`, in EBCDIC;
- keyboard ID `02`;
- 256 input fields.

| Capability byte | Value | Meaning |
| --- | --- | --- |
| 0 | `3B` | Read MDT Alternate, PA1/PA2, PA3, MC/TD/transparent FCW, Read Modified Immediate Alternate |
| 1 | `31` (FC) or `30` (FG) | 27×132 and 24×80; `01` = colour |

All other bytes are zero. A type that is not a 3477 claims only 24×80.

The client does not claim extended attributes, text support, GUI, DBCS or
graphics. A Query Reply that claims too much makes the host send data
streams the device then rejects.

### Extended attributes and the 3477 ECBs

The 3477 has three extended character buffers: primary, text and colour
(`analysis_notes/spec-3477-device-protocol.md`). Each `Cell` has a plane
for each of them:

| Plane | Holds | Filled by |
| --- | --- | --- |
| `ext_primary` | highlighting and alternate character sets | WEA type 01 |
| `ext_text` | text assist / word processing | nothing yet: needs WEA type 02 and the WP-mode text structured fields (FR 15.27.4), which are not implemented |
| `ext_color` | per-character colour | WEA type 03 |

The Query Reply does **not** claim these planes until the controller drives
the ECBs; today it paints in basic mode only. A conforming host therefore
sends no WEA. The planes are kept so that the engine is ready and Save and
Restore are exact. Enable the capability bits in `Engine::query_reply()` in
the same change that makes the controller paint the ECBs.

## Operator input (FR 16)

- **Keyboard states:**
  - Normal locked: only Attn and Sys Req act.
  - Normal unlocked.
  - Pre-help error: only Attn, Help and Reset act.
  - Post-help error.
- **Unlock.** A CC1 unlock unlocks the keyboard and moves the cursor to the
  last IC, or else to the first non-bypass field, or else to 1,1.
  - In an error state, the unlock is deferred until Reset.
- **Operator errors:**
  - The error line is saved, and the error code is shown in columns 2–5
    with a reverse-image attribute.
  - The engine queues an alarm.
  - Help sends the code with the HLP flag.
  - Reset restores the error line and the previous keyboard state.
- **Editing functions:**
  - data keys, which are checked against the field type, with monocase and
    insert mode;
  - Field Exit, Field+ and Field−, with right adjust and the sign rules;
  - Field Advance and Field Backspace, cursor keys, Home, New Line;
  - Insert, Delete, Erase EOF, Erase Input;
  - Dup, Field Mark;
  - Reset, Help, Attention, Sys Req.
- **Home.** When the cursor is already at the home position, Home sends
  Record Backspace (AID `F8`), as FR 16.2.3 describes.
- **AIDs without a read.** An AID pressed while no read is pending is held
  and answered when the next read arrives.

**Deviations [design]:**

- Insert accepts a blank as well as a null in the last position.
- An AID pressed in an active right-adjust field right-adjusts the field.
  FR says such an AID is not allowed.
- Sys Req goes to the host at once, as RFC 1205 section 4.3 describes,
  instead of opening a local system-request line.
- Type-ahead is not implemented.

**Error codes.** FR names only 0005 (protected area), 0012 (insert failed),
0019 (Dup or Field Mark not allowed), 0034 and 0037. The engine also uses
0008, 0009, 0010, 0011, 0014, 0016, 0018 and 0021. Their numbers come from
the 5250 operator error code numbering as recalled from IBM operator
documentation, and are marked **[hypothesis]** in `engine.hpp` until they
are checked against the 5494 User's Guide.

## Save Screen image

The image is our own format; the host stores it opaquely and returns it in
Restore Screen. It is versioned: `"T34S"`, then the version and the total
length. After that it holds:

- the size, cursor and IC;
- the keyboard and error state;
- the SOH state;
- any pending read and held AID;
- the format table;
- the run-length-coded character, primary and colour planes;
- the saved error line.

A sign-on screen comes to a few hundred bytes. A bad or foreign image gets
sense `10050127`.

## Transport and TLS

`Transport` is the seam: `make_transport()` returns plain TCP, or the TLS
transport when `tn5250.tls` is set. TLS starts with the first byte
(implicit TLS, as IBM i's telnet server does on port 992); there is no
STARTTLS. Plain TCP on port 23 is unchanged.

### Backends

TLS uses the host's own stack, chosen at configure time by `EM34XX_TLS`:

| `EM34XX_TLS` | Linux, BSDs | Windows | macOS |
| --- | --- | --- | --- |
| `AUTO` (default) | system OpenSSL if its development files are found, else no TLS | SChannel | Network.framework |
| `ON` | system OpenSSL, configuration fails without it | SChannel | Network.framework |
| `OFF` | no TLS | no TLS | no TLS |

The presets do not set it. CMake prints a `TN5250 TLS:` status line with
the result. Without TLS, asking for `tls` fails at connect time with "this
build has no TLS support; install the OpenSSL development files ... and
rebuild".

| File | Backend |
| --- | --- |
| `tls_openssl.cpp` | the system libssl/libcrypto (1.1.1 or 3.x), found by CMake's `FindOpenSSL`, never vcpkg's |
| `tls_schannel.cpp` | SChannel through SSPI (`AcquireCredentialsHandle`, `InitializeSecurityContext`, `EncryptMessage`, `DecryptMessage`), certificates through CryptoAPI; links `secur32` and `crypt32` |
| `tls_apple.mm` | Network.framework (`nw_connection` with `nw_parameters_create_secure_tcp`: the TCP connection and TLS) and Security.framework (`SecTrust`, `SecCertificateCopyValues`); Objective-C++ with ARC; links `Network`, `Security`, `CoreFoundation`, `Foundation` |
| `tls_none.cpp` | the no-TLS stub |
| `tls_policy.*` | the shared certificate decision and log lines |

Licences: OpenSSL 3 is Apache-2.0 (1.1.1: OpenSSL/SSLeay), linked
dynamically from the system; SChannel is part of Windows; Network.framework
and Security.framework are part of macOS. Nothing is bundled, so a macOS
universal (arm64 + x86_64) build needs no third-party TLS library.

The Apple backend is asynchronous underneath: the connection's callbacks
run on a private serial dispatch queue and hand their results to the
session's I/O thread through a mutex and a condition variable. `connect()`
waits for the connection to become ready (10 s for TCP plus 30 s for the
handshake, together), polling the cancel flag every 100 ms and cancelling
the connection when it is set. `recv()` keeps at most one
`nw_connection_receive` outstanding and only while its buffer is empty
(so an idle reader keeps TCP's flow control), and returns 0 on a timeout
without losing what arrives later. `send()` waits up to 30 s for the
send to complete. A connection that goes to the *waiting* state
(refused, no route) is treated as failed, as a socket connect would be.
The macOS deployment target is 11.0 (`CMAKE_OSX_DEPLOYMENT_TARGET`, set
before `project()` unless given).

### Certificate checking

No backend fails the handshake over the certificate. Each finishes it,
collect the leaf certificate (subject, issuer, validity period, SHA-256 of
its DER encoding), whether the chain and host name verify (*trust*), and
whether it is inside its validity period and not revoked (*validity*, see
"Validity and revocation" below), then `tls_accept_peer()` applies the
configuration. For a certificate with no validity error:

| Setting | Accepts |
| --- | --- |
| `tls_verify = "system"` (default; also `true`) | a chain to a trusted root that names the host |
| `tls_verify = "none"` (also `false`; `--tn5250-tls-insecure`) | anything |
| `tls_cert_sha256 = "AB:CD:..."` (`--tn5250-tls-pin`) | exactly that leaf certificate, even if its chain does not verify; any other certificate is refused even if it does |

A pin and `tls_verify = "none"` together are a configuration error.

Trusted roots:

- **Linux**: OpenSSL's default verify paths (`SSL_CERT_FILE`,
  `SSL_CERT_DIR`, else the library's `OPENSSLDIR`, which is the
  distribution's store), then the first distribution bundle found
  (`/etc/ssl/certs/ca-certificates.crt`, `/etc/pki/tls/certs/ca-bundle.crt`,
  ...).
- **Windows**: the Windows certificate store. SChannel runs with
  `SCH_CRED_MANUAL_CRED_VALIDATION`; the transport takes the server
  certificate (`SECPKG_ATTR_REMOTE_CERT_CONTEXT`) and checks it with
  `CertGetCertificateChain` and `CertVerifyCertificateChainPolicy(CERT_CHAIN_POLICY_SSL)`
  for the server name. Certificates an administrator has deployed to the
  machine's or user's root store are therefore trusted, and Windows'
  automatic root update applies.
- **macOS**: the system's trust settings (the System Roots, and the
  certificates a user or a configuration profile has marked trusted in the
  keychains). The verify block given to `sec_protocol_options_set_verify_block`
  only records the server's `SecTrust` and completes with yes; after the
  handshake a fresh `SecTrust` is built from the certificates the server
  sent, with `SecPolicyCreateSSL` for the host name, and evaluated with
  `SecTrustEvaluateWithError` (network fetches allowed, for missing
  intermediates). `chain_error` is the system's description with its
  `OSStatus` ("“localhost” certificate is not trusted (OSStatus -67843)",
  "... certificate name does not match input (OSStatus -67602)").
- **`ca_file`** (all): extra PEM certificates. With OpenSSL they join the
  store; with SChannel they are offered to chain building, and a chain that
  ends in one of them counts as trusted; on macOS they are added as anchors
  next to the system's (`SecTrustSetAnchorCertificates` with
  `SecTrustSetAnchorCertificatesOnly(false)`).

The host name goes out as SNI and is checked against the certificate
(subjectAltName; an IP address against IP entries).

### Validity and revocation

Trust and validity are separate questions with separate answers.
`PeerCertificate::chain_ok` / `chain_error` are about trust only: a chain
to a trusted root that names the host. Validity is `expired`,
`not_yet_valid`, `revoked`, `revocation_checked` (with `revocation_note`
when it is false) and `validity_errors`: one exact line per failure with
the platform's own code or text, for the leaf and for any other
certificate in the chain. A certificate that is merely expired has trust
OK and one validity error; a valid self-signed one has trust failed and no
validity error; one that is both has both.

A trust failure is what self-signed and private-CA servers produce, and
its answer can be remembered (a pin, `ca_file`). Accepting a validity
failure supports no such set-up: it is an override for one connection,
asked for every time and never recorded.

`tls_accept_peer()` with a validity error (expired, not yet valid,
revoked):

| Configuration | With a trust handler | Without one |
| --- | --- | --- |
| `tls_verify = "none"` | accepted; the errors are logged as warnings | the same |
| `"system"`, no pin | asked (`TlsTrustProblem::Invalid`) | refused; the error lists every failure |
| pin matches | asked (`Invalid`): a pin does not cover validity | accepted with a warning naming the errors, **except revoked: refused** |
| pin does not match | asked (`Invalid`, the mismatch is in the list) | refused |

An `Invalid` request carries every error in `TlsTrustRequest::errors`: the
validity errors, then the trust or pin failure if there is one too. Only
`Reject` and `AcceptOnce` mean anything; `AcceptPermanently` is treated as
once, and nothing is pinned.

A revocation status that could not be determined (the CRL or OCSP server
out of reach, no revocation information in the certificate, no stapled
response) is a soft failure: one info line (`TLS certificate revocation
status not checked: ...`), no question, no error. Enterprise networks
often cannot reach a CA's servers, and private-CA certificates often name
none. Only a definite "revoked" is an error.

What each backend checks:

- **SChannel** (the Windows client): `CertGetCertificateChain` with
  `CERT_CHAIN_REVOCATION_CHECK_CHAIN_EXCLUDE_ROOT |
  CERT_CHAIN_REVOCATION_ACCUMULATIVE_TIMEOUT` and
  `dwUrlRetrievalTimeout` = 6 s for all retrievals of the chain together,
  so Windows' own CRL / OCSP checking (and its cache) decides. It runs on
  the session's I/O thread after the handshake: an unreachable server can
  add up to that long to a connect. The chain's and each element's
  `TrustStatus.dwErrorStatus` give the validity result
  (`CERT_TRUST_IS_NOT_TIME_VALID`, with each certificate's
  NotBefore / NotAfter against the clock to tell expired from not yet
  valid; `CERT_TRUST_IS_REVOKED`; `CERT_TRUST_REVOCATION_STATUS_UNKNOWN`
  and `CERT_TRUST_IS_OFFLINE_REVOCATION` are the soft case).
  `CertVerifyCertificateChainPolicy(CERT_CHAIN_POLICY_SSL)` is then called
  with dates and revocation ignored (`fdwChecks`:
  `SECURITY_FLAG_IGNORE_CERT_DATE_INVALID | SECURITY_FLAG_IGNORE_REVOCATION`;
  `dwFlags`: the `IGNORE_ALL_NOT_TIME_VALID` and `IGNORE_ALL_REV_UNKNOWN`
  groups), so its single error code is about trust: root, name, signature,
  usage. The `ca_file` retry adds `SECURITY_FLAG_IGNORE_UNKNOWN_CA` as
  before. A chain the policy passes is still refused when its status has
  `CERT_TRUST_IS_PARTIAL_CHAIN`, `CERT_TRUST_IS_NOT_SIGNATURE_VALID`, or
  `CERT_TRUST_IS_UNTRUSTED_ROOT` with a root that is not a `ca_file` one.
  `CERT_CHAIN_PARA` is passed in its Windows Vista / 7 extended layout
  (through `pftCacheResync`), declared locally.
- **OpenSSL** (the developer builds): the verify callback collects every
  error instead of the first; `X509_V_ERR_CERT_HAS_EXPIRED` and
  `X509_V_ERR_CERT_NOT_YET_VALID` (and the leaf's own dates) become
  validity errors, the rest the trust result. Revocation: only a stapled
  OCSP response is looked at. The client asks for one
  (`status_request`), verifies it against the trust store
  (`OCSP_basic_verify`), finds the single response for the leaf and checks
  its update times; "revoked" is a validity error, "good" is
  `revocation_checked`. No staple, or one that does not verify, is not
  about this certificate or is out of date, is the soft case. No CRL is
  fetched and no OCSP server contacted, and only the leaf is covered.
- **Apple** (macOS): validity periods are compared by the backend itself:
  the leaf's dates and those of every other certificate of the chain the
  evaluation built (`SecCertificateCopyValues`) against the clock, one
  line each (`errSecCertificateExpired`, `errSecCertificateNotValidYet`).
  When the trust evaluation failed with a date error, it is repeated with
  `SecTrustSetVerifyDate` at a moment at which every certificate is valid
  (failing one, the leaf), so the trust answer leaves the dates out; a
  date error that remains is left to the validity lines. Revocation: a
  second evaluation with `SecPolicyCreateBasicX509` and
  `SecPolicyCreateRevocation(kSecRevocationUseAnyAvailableMethod |
  kSecRevocationRequirePositiveResponse)`, network access allowed, so
  macOS's own OCSP / CRL checking and caches decide for the whole chain.
  Success is `revocation_checked`; `errSecCertificateRevoked` (from this
  evaluation or the SSL one) is a validity error; anything else is the
  soft case (`errSecIncompleteCertRevocationCheck`: "macOS had no OCSP or
  CRL answer for it"). An untrusted chain is not asked about revocation.
  Both evaluations run on the session's I/O thread after the handshake,
  so a slow revocation server delays the connect (hypothesis: by macOS's
  own fetch timeouts; not measured).

Observed (2026-11-23, macOS 26.6.2, arm64) with `tn5250-probe` of a
debug build against a local `openssl s_server` (OpenSSL 3): a self-signed
certificate is refused ("“localhost” certificate is not trusted (OSStatus
-67843)"; revocation "a self-signed certificate has no issuer to revoke
it"); pinned, it is accepted; a wrong pin is refused; `--insecure` accepts
it with the warnings; a leaf from a `ca_file` CA verifies, with revocation
undetermined (`errSecIncompleteCertRevocationCheck`: the test CA names no
OCSP or CRL server); the same leaf without `ca_file` is refused as not
trusted, and one for another host name as "certificate name does not
match input (OSStatus -67602)"; an expired leaf from the `ca_file` CA
(whose own validity starts after the leaf's ended) is refused with
exactly one error, "The certificate expired on 2024-03-01 12:00:00 UTC
(errSecCertificateExpired, -67818)", trust OK; an expired self-signed one
lists both; a pinned expired one is accepted with the warning. Protocol
bounds: a TLS 1.0-only server is refused at the default minimum ("bad
protocol version (OSStatus -9836)") and negotiates `TLSv1
ECDHE-RSA-AES256-SHA` with `--tls-min 1.0` (with the legacy warning);
`--tls-min 1.3` against a TLS 1.2-only server and `--tls-max 1.2` behave
as configured. Refused and unresolvable hosts give "cannot connect to
localhost:47999 (Connection refused)" and "cannot resolve
no-such-host.invalid". Not tested: a certificate that is actually revoked,
a slow or unreachable revocation server, the trust handler (no front end
on macOS yet at the time).

Observed (November 2026) with the Windows builds' `tn5250-probe.exe` under
wine 9.0 against a local `openssl s_server`: a `ca_file` certificate that
is valid verifies, with the revocation line (wine reports
`CERT_TRUST_IS_OFFLINE_REVOCATION` for a certificate that names no CRL);
expired and not-yet-valid ones are refused with exactly the validity error
(trust OK); an expired self-signed one lists both errors; a pinned expired
one is accepted with the warning; a certificate from a CA that is not
trusted and not sent is refused (wine's SSL policy alone passed it, hence
the status check above). Not tested: real Windows, a certificate that is
actually revoked, a CRL server that is slow or down (hypothesis from the
API documentation: the status is then unknown or offline and the connect
is delayed by at most the retrieval timeout).

Log lines (`tn5250` category, and the session log that `tn5250-probe`
prints):

```
TLS negotiated TLSv1.3 TLS_AES_128_GCM_SHA256                                   (info, always)
TLS server certificate: subject CN=pub400.com; issuer CN=Sectigo ...; expires 2027-04-18 23:59:59 UTC
TLS server certificate SHA-256 fingerprint: DC:F3:AE:...:AA:B8  (tls_cert_sha256 / --tn5250-tls-pin)
TLS certificate revocation status not checked: the server stapled no OCSP response, ...   (info)
TLS certificate is not valid: The certificate expired on 2024-03-01 12:00:00 UTC (...)      (warning, one per error)
```

The fingerprint line is a warning whenever verification is off or fails,
and its value is in the form the pin option takes, ready to paste. When the
certificate verifies, the fingerprint is still logged at info level.

Fingerprints are parsed case-insensitively, with or without `:` (or space
or `-`) between byte pairs, and with an optional `SHA256:` prefix
(`util/fingerprint.*`).

### Asking the user: the trust hook

When the configuration refuses a certificate (system verification failed,
it is not the pinned one, or it is not valid), a front end can decide instead
(`tn5250/tls_trust.hpp`). `Transport::set_trust_handler()` installs a
`TlsTrustHandler`; `tls_accept_peer()` calls it with a `TlsTrustRequest`
(host, port, station address, the `PeerCertificate` with subject, issuer,
validity, SHA-256 and chain status, the problem (`Unverified`,
`PinMismatch` or `Invalid`), a one-line reason and the list of errors) and
gets `Reject`, `AcceptOnce` or `AcceptPermanently`. The handler runs on the
session's I/O thread after the handshake has finished, and may block until
the user answers; rejecting keeps the configured error. Recording a
permanent decision (pinning the fingerprint) is the caller's business.

The plumbing: `tn5250::Client::set_tls_trust_handler()`;
`wsc::BridgeOptions::tls_trust` (each display station's client gets it with
its station address filled in); `HostLink::set_tls_trust_handler()` stores
it in a `TlsTrustBroker` that the application's bridge factory reads, and
the broker gives every new bridge a wrapper that remembers the certificates
the user accepted, so the bridge's automatic reconnects do not ask again
while a new `connect()` does. `Invalid` requests go round that memory in
both directions: each one reaches the handler, an accepted one is not
remembered, and a certificate remembered from an earlier trust decision is
asked about again once it is not valid. So is every reconnect. Without a handler (the SDL front end, the
monitor, `tn5250-probe` today) nothing changes. The SChannel, OpenSSL and
Apple backends all feed it; under SChannel the reason is the
`CertVerifyCertificateChainPolicy` error (`CERT_E_UNTRUSTEDROOT`,
`CERT_E_CN_NO_MATCH`, `CERT_E_WRONG_USAGE`...), named in `chain_error_text()`.

`tls_fetch_certificate()` connects, takes the certificate whatever it is
and closes again: what a "Fetch" button needs. `Transport::peer_certificate()`
gives the certificate of the last handshake to any caller.

### Protocol versions

`tls_min_version` (default `"1.2"`) and `tls_max_version` (default `"any"`)
take `"ssl3"`, `"1.0"`, `"1.1"`, `"1.2"`, `"1.3"` (also `"TLSv1.2"` and the
like); `--tn5250-tls-min` / `--tn5250-tls-max` set them from the command
line, and a `[[twinax.station]]` entry may override both for its session
(`apply_station_tls()`), as well as `tls` itself (`tls = false`: that
session is plain telnet even when `[tn5250]` uses TLS, and the pinned
certificate and CA file are dropped for it; `tls = true`: TLS for that
session only). A minimum above the maximum is an error. Old
IBM i / OS/400 releases often speak only TLS 1.0 or 1.1, some only SSLv3.

- **OpenSSL**: `SSL_CTX_set_min/max_proto_version`. Below 1.2 the
  connection's security level drops to 0 (`@SECLEVEL=0`), because OpenSSL 3
  refuses TLS 1.0/1.1 and SHA-1 signatures at its default level, and a
  warning says a legacy protocol is enabled. SSLv3 needs a libssl built
  with it; most distributions build without, and the error says so.
- **SChannel**: the range maps to `grbitEnabledProtocols`
  (`SP_PROT_SSL3_CLIENT` ... `SP_PROT_TLS1_2_CLIENT`) in `SCHANNEL_CRED`.
  TLS 1.3 needs the newer `SCH_CREDENTIALS` API, which Windows 7 lacks, so
  this backend offers 1.2 at most and refuses `tls_min_version = "1.3"`.
  Windows' own policy (the SCHANNEL registry keys, Group Policy) can still
  disable a protocol system-wide, whatever is configured here.
- **Apple**: `sec_protocol_options_set_min_tls_protocol_version` /
  `..._max_...`, TLS 1.0 to 1.3. Network.framework has no SSL 3.0: a
  minimum of `"ssl3"` offers TLS 1.0 and up (with a warning), a maximum of
  `"ssl3"` is refused at connect time. Below 1.2 the legacy warning is
  logged; the cipher suites are the system's.

## tn5250-probe

```
tn5250-probe HOST [PORT] [--ttype TYPE | --mono] [--devname NAME]
             [--codepage 37|500|273] [--env NAME=VALUE] [--timeout S] [--fields]
             [--tls [--insecure | --pin SHA256] [--ca FILE] [--tls-min V] [--tls-max V]]
```

`--tls` (implied by the other TLS options) makes the default port 992.

The probe:

1. connects and prints the negotiation log;
2. waits until the host has written a screen and armed a read;
3. prints the screen through the chosen code page;
4. disconnects.

It never types anything, so it never signs on. Against the public server
pub400.com:23 (or `pub400.com --tls`, port 992), it negotiates
`IBM-3477-FC` and prints the sign-on panel.
That panel has two input fields; the password field is non-display.

## Pointing device (FR chapter 17)

A display with a mouse reports button events to its controller: pressed,
released and double click, for three buttons, with the keyboard's Shift
state, and the position of the pointer. What a click does is the
controller's decision. The host sees an ordinary AID, or nothing; no mouse
data travels over TN5250. `DisplaySession::pointer_event()` is that
decision, written from FR chapter 17 **[doc]**; the hot-spot patterns are
**[design]**, because the FR gives examples and no grammar.

An event is ignored when the keyboard is locked or no read is pending. In
operator error state only a left press on the error line acts: it is Reset.

Unshifted left button pressed, in the FR's order (first match wins):

| Step | Condition | Action | Here |
| --- | --- | --- | --- |
| 1 | operator error state | Reset if on the error line, else nothing | yes |
| 2 | on a selection field choice | cursor to the pointer, Space Bar | no: needs Write Data Structured Field |
| 3 | on a scroll bar | Roll AID, or drag the slider | no: same |
| 4 | in a mouse selection entry field (FCW `8Ann`) | cursor to the pointer, AID `nn` | yes |
| 5 | in a light-pen field | as a light-pen tip switch | no |
| 6 | event programmed (Programmable Mouse Buttons) | as programmed | no |
| 7 | hot spot, outside any entry field | see below | yes |
| 8 | pull-down cancel mode | cursor to the pointer, the cancel AID | no |
| 9 | otherwise | text cursor to the pointer, anywhere on the screen | yes |

Hot spots (step 7), tried in this order:

| Text under the pointer | AID | Pattern **[design]** |
| --- | --- | --- |
| command key text, `F12=Cancel` | that F key | `F`, one or two digits, `=`, not after a letter or digit; the description runs to two blanks or the next key |
| `+` / `-` | Roll Up / Roll Down | the sign stands alone or follows `More` (`More-/+`); not inside a word or on a number |
| `More` / `Bottom` | Roll Up / Roll Down | the whole word, any case (English only, as in the FR) |
| menu choice, `2. Office tasks` | Enter | 1 to 5 digits and a period after a blank, with the choice's text. The number replaces the contents of the entry field the text cursor is in, or else of the first one |

The other events:

- **Left double click:** Enter, if the press before it positioned the text
  cursor (step 9) and the cursor is still there.
- **Right button pressed:** Roll Down on `More` or `Bottom`; nothing
  elsewhere.
- **Shifted events** are copy and paste (the copy is kept in the display).
  Not implemented.
- Everything else is ignored, as in the FR when no button is programmed.

The Query Reply is unchanged: none of this needs the host to know there is
a mouse.

Where the events come from is the station controller's business
(`docs/twinax-bridge.md`, "Pointing device"): a 3486/3487 with a mouse
reports them once the controller has switched that on.

Tested [obs] with the 3487 image and `--mouse` against the Solstice
emulator's twinax stations (OS/400 V4R5, TN5250, terminal type
`IBM-3179-2`): a left press in an entry field of the Sign On panel moves
the text cursor there and typing lands at that column; a double click
there sends Enter; a left press on the error line resets an operator
error; a left press on a choice of "IPL or Install the System" keys its
number and Enter; a left press on `F12=Cancel` sends F12. Not tested
against a host: the right button on `More...`, the scrolling signs, a
mouse selection entry field.
